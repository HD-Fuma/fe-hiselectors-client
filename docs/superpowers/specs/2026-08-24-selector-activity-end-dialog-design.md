# 셀렉터스 활동 종료 확인 팝업 설계

## 목표

회원정보 화면의 브라우저 기본 `window.confirm`을 서비스 내부 팝업으로 교체한다. 종료 요청과 이후 정산 처리 방식은 변경하지 않는다.

## UI

- 활동 종료 버튼을 누르면 기존 `group-dialog` 스타일의 모달을 연다.
- 제목은 `셀렉터스 활동을 종료할까요?`로 표시한다.
- 본문은 아래 두 줄로 표시한다.
  - `종료 즉시 셀렉터스 자격이 사라지며 이 작업은 되돌릴 수 없습니다.`
  - `미정산 금액은 예정대로 정산됩니다.`
- 하단에 `취소`와 `활동 종료` 버튼을 둔다.

## 구조와 동작

- `MemberInfoScreen` 전용 팝업 컴포넌트를 같은 파일에 두어 공용 추상화와 새 의존성을 만들지 않는다.
- 기존 `group-dialog` CSS와 `useModalFocus`를 재사용해 최초 포커스, Tab 순환, Escape 닫기를 유지한다. 취소와 Escape에서는 호출 버튼으로 포커스를 돌려준다. 확인 경로는 같은 렌더에서 호출 버튼이 비활성화되므로 포커스 복귀 대상에서 제외한다.
- 팝업은 `role="dialog"`, `aria-modal`, `aria-labelledby`, `aria-describedby`를 제공한다.
- 화면은 팝업 열림 상태를 관리한다. `취소` 또는 Escape는 팝업만 닫고 API를 호출하지 않는다.
- `활동 종료`를 누르면 확인 팝업을 먼저 닫은 뒤 기존 `handleEndActivity`를 실행한다. 따라서 성공·오류 알림과 확인 팝업은 동시에 렌더링되지 않는다.
- 팝업이 먼저 닫히므로 세션 없음, 세션 교체 감지, 401/403 리다이렉트 등 조기 반환 경로에서도 별도의 팝업 정리가 필요하지 않다.
- 요청 중에는 기존 화면의 활동 종료 버튼이 비활성화되고 `종료 처리 중...`으로 표시되어 중복 요청을 막는다.
- 세션 교체·권한 갱신·401 처리 등 기존 비동기 보호 로직은 변경하지 않는다.

## 오류 처리

- API 실패 메시지는 기존 서비스 알림 팝업으로 표시한다.
- 기존 `isEndingActivity` 가드로 중복 요청을 막는다.

## 테스트

- 활동 종료 버튼이 브라우저 `confirm` 대신 서비스 팝업을 여는지 확인한다.
- 본문 두 문장 사이에 실제 줄바꿈이 있는지 확인한다.
- 취소와 Escape 시 DELETE가 호출되지 않는지 확인한다.
- 확인 시 기존 DELETE·권한 재조회·성공 알림 흐름이 유지되는지 확인한다.
- 확인 팝업이 성공·오류 알림보다 먼저 닫히는지 확인한다.
- DELETE 응답 대기 중 화면의 활동 종료 버튼이 비활성화되고 `종료 처리 중...`으로 표시되는지 확인한다.
- 요청 중 추가 클릭에도 DELETE가 한 번만 호출되는지 확인한다.
- 기존 비동기 세션 경합 테스트는 서비스 팝업의 확인 버튼을 누르는 방식으로 유지한다.
